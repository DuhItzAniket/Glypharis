This is the working plan for building GLYPHARIS: a lightweight document OCR engine (text-line detector +
CTC line recognizer) trained and evaluated entirely on one laptop (RTX 4050 Laptop, 6 GB VRAM, 16 GB RAM).
It turns the original project brief into phases with concrete tasks, deliverables, and **measurable exit
criteria**. Phase numbering follows the brief (0–23) so requirements stay traceable (see §8).

The research background behind these choices is in [`research/approach_survey.md`](../research/approach_survey.md).

---

## 1. Goal

Produce a reproducible, honestly evaluated OCR engine that:

1. reads English printed text from scanned, photographed, or degraded document images;
2. returns structured output (text, lines, boxes, confidence, timing) through `GlypharisOCR.predict()`;
3. trains, resumes, and evaluates on the laptop above without exceeding ~4.5 GiB of VRAM;
4. comes with a research record good enough to write a paper from: hypotheses written before
   experiments, controlled ablations, baselines, error analysis, negative results included.

**Priority order** (from the brief): scientific correctness → reproducibility → recognition quality →
robustness → performance → deployment readiness. When two goals conflict, the earlier one wins.

## 2. Ground rules

- **Phase gate.** Every phase ends with the ten-step gate in [WORKFLOW.md §3](WORKFLOW.md#3-the-phase-gate).
  "Looks correct" is not verification.
- **No fabricated numbers.** Metrics are generated by scripts and copied with their experiment ID.
- **Test discipline.** Test splits are touched only in Phases 5, 14 and 22, and every access is logged in
  [`research/test_access_log.md`](../research/test_access_log.md).
- **One variable at a time** in causal comparisons; controls are named by experiment ID.
- **Pre-registration light.** Each experiment's hypothesis and success criterion go into
  [`research/hypotheses.md`](../research/hypotheses.md) *before* it runs.
- **Hardware honesty.** Plan for ~4.5 GiB of free VRAM (measured idle free memory is 4.96 GiB). Every config
  is validated by a short dry run that records peak memory before a long run starts.
- **Independence from consumers.** No BookWorm code, config, or naming inside the package.

| RQ | Question | Primary evidence | Phases |
|---|---|---|---|

| RQ2 | How much does synthetic data help recognition, and **does its domain matter** (scene-text SynthText vs document-style GlyphSynth) at equal budget? | Scaling curves 25K→250K for both sources | 12 |
| RQ3 | Which degradation augmentations improve robustness on degraded documents? | Corruption-suite CER per augmentation family | 7, 11 |
| RQ4 | How does GLYPHARIS compare with Tesseract, PaddleOCR (PP-OCRv5) and TrOCR-Small? | Same data, same metrics, same normalisation, with latency and memory | 5, 14, 16 |
| RQ5 | Which failure modes dominate, and do they come from the detector or the recognizer? | Categorised error report with oracle-detector analysis | 9, 15 |
| RQ6 | How does document-domain performance differ from scene-text performance? | GDC/FUNSD/OmniDocBench vs HierText/IIIT5K | 14 |
| RQ7 | What is the accuracy / latency / memory trade-off for local deployment? | Pareto table across model sizes, input resolutions, precision, and ONNX/quantised variants | 16, 17 |
| RQ8 (new) | Is the raw CTC confidence calibrated, and does temperature scaling fix it? | ECE and reliability diagrams on validation and external data | 10, 14 |

## 4. Data strategy (summary)

Full provenance, licences, and citations are in [DATASETS.md](../DATASETS.md). Roles are fixed in
[ADR-0005](decisions/ADR-0005-evaluation-data-roles.md) and must not drift.

| Role | Sources | Notes |
|---|---|---|
| **Train (real)** | HierText train (lines) | Real photographed text with line/paragraph hierarchy |
| **Train (synthetic, scene)** | SynthText subsets 25K / 50K / 100K / 250K images | As specified in the brief |
| **Train (synthetic, document)** | **GlyphSynth**: our renderer for document-style text lines and pages (open-licence fonts + public-domain / permissive text + document degradations) | Added by [ADR-0003](decisions/ADR-0003-document-domain-synthetic-data.md). Exact labels and unlimited volume, matched to the target domain |
| **Validation** | HierText validation (lines), GlyphSynth-val (held-out fonts *and* texts) | Model selection, early stopping, and HPO only use these |
| **Internal test** | HierText test, if public ground truth exists (else see DATASETS.md fallback), GDC | Phases 5 / 14 / 22 only |
| **External test** | IIIT5K (words), FUNSD (forms), OmniDocBench (documents), SROIE (receipts, low priority) | Never used for training or tuning |
| **Reference only** | DocVQA | Its OCR text is machine-generated, so it is not used as CER ground truth (see DATASETS.md) |

**GDC: Glypharis Document Challenge.** This is the brief's "BookWorm-OCR-Challenge", under a neutral name.
It is a small (target 100–150 pages), manually curated, **frozen** test set that represents the target
environment: clean scans, old scans, low-resolution, photographed, rotated, skewed, multi-column, pages with
figures and captions, number- and punctuation-heavy pages, and low-contrast pages. Ground truth is built
mainly by *print-and-capture*: born-digital, openly licensed PDFs give exact text, the pages are printed,
then scanned and photographed. A small manually transcribed subset is added for real old scans. Source
documents for GDC go on an exclusion list so they never appear in any training corpus. Built in Phase 4,
frozen before Phase 5.

## 5. Compute budget

Order-of-magnitude **estimates**. They will be replaced with measured throughput after Phase 6 and Phase 8,
and the plan re-budgeted if they are off by more than 2×.

| Block | Runs (core) | Est. GPU-hours | Notes |
|---|---|---|---|
| Recognizer baseline + sanity runs (P6) | 3–5 | 10–20 | Overfit-one-batch, LR range test, first full run |
| Recognizer improvement (P7) | 8–12 | 30–60 | Short-budget runs; HPO on validation only |
| Detector baseline + ablation (P8) | 3–5 | 20–40 | DBNet on HierText at 640² crops |
| Robustness study (P11) | 4 × 3 seeds | 20–40 | A/B/C/D augmentation arms |
| Synthetic study (P12) | 8 (+ seeds at 2 points) | 30–60 | 2 sources × 4 sizes |
| Ablation + final model (P13) | 5 × 3 seeds | 30–60 | |
| Evaluation / efficiency (P5, P14, P16) | inference only | 5–15 | Baselines are CPU-heavy |
| **Total** | | **~150–300** | Roughly 3–6 weeks of overnight runs |

Rules: every long run is preceded by a ≤10-minute dry run that records peak VRAM and throughput.
Runs are resumable, so laptop sleep or reboots cost minutes, not days. Thermals (GPU temperature and clocks)
are logged so slowdowns can be attributed.

## 6. Experiment design defaults

Details in [EXPERIMENT_PROTOCOL.md](EXPERIMENT_PROTOCOL.md).

- **Primary metric:** validation CER (recognizer, end to end) and line-level F1 at IoU ≥ 0.5 (detector).
  Always reported together with WER, NED, word / sequence accuracy, and precision / recall.
- **Seeds:** 3 seeds for comparisons that go into the paper's main tables. Single-seed runs are labelled
  exploratory.
- **Uncertainty:** 95% bootstrap confidence intervals (resampling lines or pages), plus a paired bootstrap
  test for model-vs-model claims.
- **Budget matching:** compared arms get the same number of optimisation steps (not epochs) unless the
  comparison is about budget.
- **Diagnostics on every run:** over/underfitting flags, CTC blank-collapse detection, gradient health,
  NaN/Inf guards, and a generated run report that names the best epoch vs the final epoch.

## 7. Phases

Each phase lists **Objective, Tasks, Deliverables, Exit criteria**. Effort is in focused working sessions
(S) and GPU-hours (GPU-h), both estimates. Branch: `phase/NN-name`.

**Execution order** ([ADR-0008](decisions/ADR-0008-usable-engine-first.md)): phases are listed in brief
order but run as `0–10 → 17 → 18 → 20` (= v0.1, a usable engine), then `11 → 12 → 13 → 14 → 15 → 16 →
17/18/20 re-run on the final model → 19 → 21 → 22 → 23` (= v1.0). v0.1 uses the Phase 7 recognizer and
Phase 8 detector, is evaluated on validation data only, and needs only the SynthText subset used in the
recognizer mix. Inference is CPU-first: CPU latency through ONNX Runtime is the primary efficiency number,
with a concrete target set from the Phase 5 baseline measurements.

### Phase 0 — Repository discovery and planning ✅
- **Objective:** understand the environment and the problem; produce the plan.
- **Tasks:** inspect machine, Python, CUDA, Git; survey methods and datasets; write plan, roadmap, protocol,
  risk register, ADRs, research log, paper skeleton.
- **Deliverables:** `README.md`, `docs/*`, `research/*`, `configs/README.md`, `reports/README.md`.
- **Exit criteria:** docs pushed to `main`; environment recorded with measured values; no training code.
- **Effort:** 1 S, 0 GPU-h.

### Phase 1 — Environment and reproducibility
- **Objective:** a reproducible, tested foundation that later phases build on.
- **Tasks:**
  1. `.venv` with pinned dependencies (`pyproject.toml` + lock/constraints file); decide the torch/CUDA
     build by measurement (keep 2.5.1+cu121 or move to a newer cu12x build supported by driver 566.24).
  2. `glypharis.utils`: global seeding (`random`, `numpy`, `torch`, CUDA, `PYTHONHASHSEED`, cuDNN flags,
     worker seeding), device selection with CPU fallback, AMP policy (bf16 → fp16 → fp32), VRAM / RAM /
     temperature monitor, git-commit capture, structured logging.
  3. `glypharis.config`: YAML → typed dataclasses, `inherits:` merging, CLI overrides
     (`--config --seed --resume --device`), strict validation (unknown keys are errors).
  4. `scripts/env_report.py` writes `reports/environment/` (driver, CUDA, cuDNN, package versions, GPU
     probe, AMP check, CTC fp32 check).
  5. Tooling: ruff, mypy (package only), pytest, pre-commit (optional).
  6. CI: GitHub Actions on push/PR (install CPU-only torch → ruff → mypy → pytest → config validation).
     CPU only, target < 10 min.
- **Exit criteria:**
  - Determinism test: two CPU runs of a toy model with the same seed produce bit-identical losses for 50
    steps; on CUDA, a documented tolerance.
  - Config validator rejects an unknown key and a wrong type (tests).
  - `env_report.py` runs on the laptop and in CI.
  - CI green on `main`.
- **Effort:** 2–3 S, <1 GPU-h.

### Phase 2 — Dataset acquisition
- **Objective:** reproducible download and provenance for every dataset.
- **Tasks:**
  1. `scripts/download_datasets.py --dataset NAME [--subset]`: creates `data/{raw,interim,processed,manifests}`,
     skips existing data, verifies checksums where published (SHA-256 recorded on first download otherwise),
     logs status, and writes `data/manifests/<dataset>.json`.
  2. `data/DATASET_MANIFEST.yaml`: dataset, version, source, licence, download date, samples, preprocessing,
     split, as the brief requires.
  3. `DATASETS.md` cards updated with actual counts measured after download.
  4. Disk plan: SynthText is the largest download; extract only what the 250K study needs and stream-convert
     its annotation file (RAM risk, see RISK_REGISTER R-04).
  5. Licence check recorded per dataset *before* download; anything unclear is parked, not downloaded.
- **Exit criteria:** every downloaded dataset has a manifest with file counts and hashes; a re-run of the
  downloader is a no-op; DATASETS.md has no "TBD" for downloaded sets; CI green (the downloader is unit-tested
  against a fake source).
- **Effort:** 2 S + download time.

### Phase 3 — Data audit
- **Objective:** know the data before training on it.
- **Tasks:**
  1. `scripts/audit_data.py` computes per-dataset statistics: image size, aspect ratio, text length, character
     frequency, characters per word, words per line, box sizes, rotation, blur (variance of Laplacian), and
     brightness/contrast.
  2. Plots to `reports/data_analysis/<dataset>/`.
  3. Quality checks: corrupt images, missing or empty labels, invalid / out-of-range boxes, invalid Unicode,
     abnormal aspect ratios, exact and near-duplicate images (perceptual hash), and **cross-split duplicates**.
  4. Nothing is silently dropped. Every flagged sample lands in `reports/data_quality_report.md` with a
     decision (keep / fix / exclude + reason), and exclusions go into a versioned exclusion list.
- **Exit criteria:** quality report generated for every downloaded dataset; zero unexplained exclusions; zero
  cross-split near-duplicates left unhandled; plots committed; CI green.
- **Effort:** 2 S.

### Phase 4 — Preprocessing, charset, synthetic data, GDC
- **Objective:** training-ready data with documented transformations.
- **Tasks:**
  1. **Normalisation** (`glypharis.data.text`): Unicode NFC by default (NFKC only in the evaluation
     "normalised" track), whitespace collapsing, control-character removal, an explicit typographic map
     (curly quotes, dashes, ligatures), and no case folding in training labels. Store `original_text` and
     `normalized_text`.
  2. **Charset** (`data/manifests/charset.json`): derived from training-split character frequencies, with a
     minimum-count threshold, explicit unknown handling, special tokens, version, and normalisation rules.
     Configurable per experiment.
  3. **Annotation conversion** to one internal format (page JSON: lines with polygon, text, ids, plus a
     document id for grouped splitting).
  4. **Line crops** for the recognizer: perspective-rectified crops of each line, packed into LMDB
     (or tar shards) with width metadata for bucketing.
  5. **Splits**: grouped by image/document (never page-level leakage); HierText validation carved per
     DATASETS.md if needed; split files committed with hashes.
  6. **Augmentation framework** (`glypharis.data.augment`): named presets `none | geometric | photometric |
     degradation | full`, with per-transform probability and severity in config. Document degradations come
     from Augraphy-style transforms and/or our own implementations.
  7. **GlyphSynth v1** (`glypharis.data.synth`): renders text lines (and later pages) from a licence-checked
     corpus with open-licence fonts, controlled font/size/spacing/background/degradation sampling, and exact
     labels and boxes. Held-out fonts and held-out text for its validation split.
  8. **GDC v1**: collect source documents, build print-and-capture pages, write and verify ground truth, freeze
     it (hash manifest), and add its sources to the training exclusion list.
  9. **Corruption suite** (`GLYPH-C`): fixed, seeded degradations of the validation set (blur, noise, JPEG,
     low-res, contrast, rotation, perspective, at 5 severities) for RQ3. Generated once and frozen.
- **Exit criteria:** round-trip test (convert → read back → identical text and boxes); crops visually
  spot-checked (contact sheet in reports); charset covers ≥ 99.9% of validation characters (measured);
  GlyphSynth reproducible from seed; GDC frozen with manifest; CI green.
- **Effort:** 4–6 S (GDC needs the user's help to print and capture).

### Phase 5 — Baseline systems
- **Objective:** scientific reference points before training anything.
- **Tasks:**
  1. `.venv-baselines` with Tesseract 5 (UB Mannheim build), PaddleOCR 3.x (PP-OCRv5 mobile and server
     where feasible), and TrOCR-Small (Hugging Face).
  2. `scripts/run_baselines.py` produces the same output schema as GLYPHARIS so the same evaluator scores
     everything.
  3. Three clearly separated comparisons: **detection only** (where the baseline exposes boxes),
     **recognition only** (ground-truth line crops in, text out; TrOCR's natural setting), and
     **end to end** (page in, text out).
  4. Measure CER, WER, NED, accuracy, average and p95 latency, peak RAM, and peak VRAM, on validation and
     the designated test sets (logged in the test access log).
- **Exit criteria:** `reports/baselines/` has one table per comparison type with the normalisation track
  stated; every number traceable to a `GW-BASE-NNN` ID; any baseline that could not be run is documented
  with the reason.
- **Effort:** 2–3 S, CPU-heavy.

### Phase 6 — Recognition baseline (GLYPHARIS-Rec, CRNN)
- **Objective:** a first stable recognizer with a fully instrumented training loop.
- **Tasks:**
  1. CRNN (CNN → BiLSTM → linear → CTC) per ARCHITECTURE §4.
  2. Trainer: AMP (bf16 preferred), gradient accumulation, clipping, schedulers, checkpointing
     (`best.pt`, `last.pt`, `epoch_XXX.pt`, each with model / optimizer / scheduler / scaler state, epoch,
     step, metric, resolved config, git hash, and RNG states), and resume.
  3. Diagnostics module: over/underfitting detectors, blank-collapse detection, NaN/Inf and gradient-norm
     guards, OOM handling (catch → halve batch, or abort cleanly with a report), and data-leakage assertion
     (train/val id overlap = 0).
  4. Run report generator: curves (loss, CER, WER, LR, grad-norm, VRAM), best-vs-final epoch, flags,
     selected checkpoint rationale, mispredicted examples.
  5. Sanity sequence before the real run: (a) overfit 64 samples to ~0 CER; (b) LR range test;
     (c) 10-minute dry run that records VRAM and throughput.
  6. GW-REC-001: CRNN on HierText lines (+ a small GlyphSynth mix as a separate run, GW-REC-002).
- **Exit criteria:** all sanity checks pass and are recorded; resume test (kill at step N, resume, metrics
  match an uninterrupted run within tolerance); the first full run finishes without NaN; the run report is
  generated automatically; validation CER is reported with a bootstrap CI; parameters, model size, and
  training time recorded; CI green (with a tiny CPU training smoke test).
- **Effort:** 3–4 S, 10–20 GPU-h.

### Phase 7 — Recognizer improvement
- **Objective:** improve the recognizer under controlled conditions; settle architecture and hyperparameters.
- **Tasks (each one an experiment ID, validation only):**
  - input height 32 vs 48; CNN depth/width; BiLSTM size; sequence downsampling;
  - optimizer (AdamW vs Adam), schedule (OneCycle vs cosine), LR, and weight decay — small HPO budget
    (≤ 12 short runs);
  - augmentation presets A–D (first pass; the full study is Phase 11);
  - **SVTR-style encoder + CTC** (GLYPHARIS-Rec-M) vs CRNN at matched budget;
  - optional TrOCR-Small fine-tune as an external reference point (not a GLYPHARIS model).
- **Exit criteria:** a chosen recognizer configuration with the evidence table; all runs have diagnostic
  reports; negative results recorded; CI green.
- **Effort:** 4–6 S, 30–60 GPU-h.

### Phase 8 — Text detector (GLYPHARIS-Det)
- **Objective:** a lightweight line detector trained and evaluated on its own.
- **Tasks:** DBNet-style model per ARCHITECTURE §3; label generation (shrink and threshold maps); polygon
  post-processing; detection metrics (precision/recall/F1 at IoU 0.5, plus the HierText-style and CLEval-style
  metrics per protocol); visual overlays (GT, prediction, false positive, false negative); ImageNet vs scratch
  backbone ablation (ADR-0007); MobileNetV3 Large vs Small.
- **Exit criteria:** overfit-one-batch passes; validation F1 reported with CI; overlays saved for each slice
  (small text, rotated, dense, multi-line, noisy background); diagnostics report generated; CI green
  (post-processing unit tests on synthetic masks).
- **Effort:** 3–4 S, 20–40 GPU-h.

### Phase 9 — Detector error analysis
- **Objective:** understand detector failures before integration.
- **Tasks:** automatic slicing by box height, rotation, density, blur, and contrast; FP/FN galleries;
  merge/split error counts (one GT line ↔ multiple predictions); threshold and unclip-ratio sensitivity on
  validation.
- **Exit criteria:** `reports/error_cases/detector/` + written findings in `research/findings.md`; fixes
  either applied (with a new experiment ID) or deferred with a reason.
- **Effort:** 1–2 S.

### Phase 10 — Full OCR pipeline
- **Objective:** `GlypharisOCR.predict(image)` end to end.
- **Tasks:** crop/rectify; batching by width; reading order (XY-cut heuristic) with explicit tests (single
  column, two columns, mixed blocks, ragged lines, rotated regions); raw confidence; temperature-scaling
  calibration fit on validation, with ECE reported before and after; page-level metrics (order-aware CER/WER
  and order-agnostic bag-of-lines F1); **oracle analysis** (GT boxes → recognizer) to separate detector from
  recognizer error.
- **Exit criteria:** pipeline unit- and integration-tested on fixtures; validation E2E metrics reported;
  calibration either validated (ECE reduced, with numbers) or confidence documented as raw; CI green with an
  inference smoke test on a tiny bundled model.
- **Effort:** 3–4 S.

### Phase 11 — Robustness training
- **Objective:** find out which degradation augmentations actually help (RQ3).
- **Design:** arms A (none), B (geometric), C (photometric), D (document degradation), E (full); 3 seeds
  each; equal steps; evaluated on clean validation **and** the frozen GLYPH-C corruption suite (CER per
  corruption × severity, plus mean corruption error).
- **Exit criteria:** results table with CIs and a paired comparison against A; a clear verdict per family
  (helps / no effect / hurts); recorded in `research/ablations.md`.
- **Effort:** 2 S, 20–40 GPU-h.

### Phase 12 — Synthetic data study
- **Objective:** measure how much synthetic data helps and whether its domain matters (RQ2).
- **Design:** recognizer trained on HierText-train + {SynthText, GlyphSynth} at {25K, 50K, 100K, 250K};
  sizes counted in *images* for SynthText as the brief specifies, and line counts reported for both
  sources so the comparison is interpretable. Equal step budgets per size. Evaluated on HierText-val,
  GlyphSynth-val, and a document-style validation slice. 3 seeds at 25K and 250K for both sources.
- **Exit criteria:** scaling plots + table (CER, WER, F1 for the detector variant if run, latency
  unchanged by design); verdict on "more data ⇒ better?" and "document vs scene synthetic?", with CIs.
- **Effort:** 2 S, 30–60 GPU-h.

### Phase 13 — Ablation study
- **Objective:** the paper's main ablation table.
- **Design:** Baseline → + augmentation → + synthetic data → + improved preprocessing → full model; one
  change per row against a named control; 3 seeds; final configuration chosen **on validation**.
- **Exit criteria:** ablation table generated; final configuration frozen
  (`configs/final/glypharis_v1.yaml`) with full reproducibility record (brief §64).
- **Effort:** 2 S, 30–60 GPU-h.

### Phase 14 — External evaluation
- **Objective:** one-shot evaluation of the frozen model on held-out and external benchmarks (RQ1, RQ4,
  RQ6, RQ8).
- **Tasks:** IIIT5K (recognizer, words), FUNSD (E2E on forms), OmniDocBench (text blocks, page-level,
  using its official protocol where compatible), HierText test (if available), GDC, SROIE (optional);
  identical runs for the baselines. Each benchmark is evaluated **once** per frozen model. Results are logged
  in the test access log.
- **Exit criteria:** benchmark tables with CIs and incompatibilities explained (granularity, normalisation,
  charset); no tuning after seeing results (any later change becomes a new model version, evaluated again
  and disclosed).
- **Effort:** 2–3 S.

### Phase 15 — Error analysis
- **Tasks:** character confusion matrix; most common character and word errors; slices by condition
  (blur, rotation, small font, low contrast, touching or broken characters, punctuation, numbers, long
  words, unusual fonts, background noise, cropping error); detector vs recognizer failure proportion (from
  the oracle analysis); representative examples.
- **Exit criteria:** `reports/error_cases/` + `research/paper/error_analysis.md` drafted from generated
  numbers.
- **Effort:** 2 S.

### Phase 16 — Efficiency optimisation
- **Tasks:** parameters, model size, CPU/GPU latency (mean, p95), throughput, VRAM, RAM, page time;
  sweeps over input resolution and batch size; preprocessing cost profile; dynamic INT8 quantisation (ONNX
  Runtime) where accuracy loss is measured and acceptable.
- **Exit criteria:** efficiency table + accuracy/latency Pareto plot (RQ7), all measured on this laptop with
  documented conditions (power mode, warm-up, thread counts).
- **Effort:** 2 S.

### Phase 17 — Model export
- **Tasks:** PyTorch release checkpoint (weights + metadata); ONNX export for detector and recognizer with
  dynamic axes; equivalence tests (max abs diff on logits within tolerance, identical decoded text on the
  validation sample, E2E CER difference ≤ an agreed epsilon).
- **Exit criteria:** export is declared successful **only** after the equivalence tests pass and are
  recorded; CI runs ONNX equivalence on the tiny model.
- **Effort:** 1–2 S.

### Phase 18 — Inference package
- **Tasks:** `GlypharisOCR.from_pretrained`, `predict`, `predict_batch`; input types (path, PIL, ndarray);
  `OCRResult` dataclass + JSON; `infer.py --image / --input-dir` → `results/*.json|*.txt`; packaging
  (`pip install -e .`).
- **Exit criteria:** API tests on fixtures; clean-venv install test; outputs match Phase 10 pipeline on the
  validation sample.
- **Effort:** 2 S.

### Phase 19 — Optional HTTP API
- **Tasks:** minimal `POST /ocr` (FastAPI or similar, single process), returning the documented schema with
  `model_version`; input size limits.
- **Exit criteria:** API tests with a test client; documented as an integration boundary only.
- **Effort:** 1 S.

### Phase 20 — Production engineering
- **Tasks:** input validation (type, size, decode errors), structured errors, logging, model loading and
  caching, configuration, version metadata, basic performance metrics.
- **Exit criteria:** failure-path tests (corrupt image, huge image, empty page, non-image); no unhandled
  exceptions in the fuzz-lite test.
- **Effort:** 1–2 S.

### Phase 21 — Research package
- **Tasks:** finalise `MODEL_CARD.md`, `DATASETS.md`, `EXPERIMENTS.md` (generated summary), and the
  `research/paper/*` sections from recorded evidence; `references.bib` complete.
- **Exit criteria:** every number in the paper notes traces to an experiment ID and report file.
- **Effort:** 2–3 S.

### Phase 22 — Final validation
- **Tasks:** clean-machine-style run: fresh clone → install → download → prepare → load model → infer →
  evaluate; record every manual step.
- **Exit criteria:** walkthrough log in `docs/FINAL_VALIDATION.md`; reproduced metrics within stated
  tolerance of the reported ones.
- **Effort:** 1–2 S.

### Phase 23 — Release v1.0
- **Preconditions:** tests and CI pass; training pipeline, inference and export verified; docs complete;
  model artifact verified (hash + equivalence).
- **Tasks:** release notes, version bump, tagged GitHub release with the model artifact (or download script
  if the artifact is too large for a release asset), with licence terms that respect the training data
  (see DATASETS.md §Licensing implications).
- **Effort:** 1 S.

## 8. Deviations from the original brief

| Change | Why | Record |
|---|---|---|
| Added **GlyphSynth** (document-style synthetic data) next to SynthText | HierText and SynthText are scene-text-oriented; the target is document pages. Makes RQ2 a domain-vs-scale study. | ADR-0003 |
| Recognizer works on **lines**, not words | Document text is line-structured; CTC handles long lines | ADR-0002 |
| DocVQA demoted to reference-only | Its OCR transcriptions are machine-generated, not human ground truth | ADR-0005, DATASETS.md |
