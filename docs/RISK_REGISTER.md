# Risk Register

Reviewed at every phase gate. L = likelihood, I = impact (H/M/L). "Trigger" is the observable signal that
the risk is materialising.

| ID | Risk | L | I | Mitigation | Trigger | Phase |
|---|---|---|---|---|---|---|
| R-01 | **VRAM budget.** Only ~4.5–5 GiB is free on the 6 GB laptop GPU (WDDM desktop + other apps). | H | M | bf16 autocast; width bucketing; gradient accumulation; mandatory 10-min dry run that records peak memory; OOM handler that saves state and exits cleanly. **Detector (Phase 8):** fixed 640² training crops; the trainer refuses to start with less than 4.0 GiB of GPU memory free, counting its own process's cached memory as free (exit 4), so it does not start while another run holds the GPU; one live trainer per process, closed and freed before the next; a dry run for each GW-DET config gated on reserved memory ≤ 4.0 GiB in training and in validation; batch-1 validation followed by emptying the cache; pre-declared fallback batch 4 × accumulation 2 for all arms | Peak VRAM > 4.5 GiB in dry run, or CUDA OOM; for the detector, reserved memory > 4.0 GiB in a dry run | 1, 6, 8 |
| R-02 | **RAM (16 GB) during data preparation.** Large annotation files and image decoding can exhaust memory. | M | M | Streaming conversion; process in chunks; pack crops into LMDB / shards; never load a whole dataset into memory | Swap usage spikes; MemoryError | 2–4 |
| R-03 | **Disk.** Extracted datasets, packed crops and synthetic data accumulate. | L | M | Free-space check with a 20 GiB margin before every download; delete interim files after packing; track usage in manifests. SynthText (41 GB) dropped (ADR-0009) | Free space < 80 GB | 2, 4, 12 |

| R-20 | **Link rot / changed dataset hosting.** | M | L | Record URLs, versions, and hashes in manifests; note mirrors | Download URL fails | 2, 22 |
| R-21 | **(Closed 2026-10-28, Phase 9: the trained kernels match the label width, median ratio 1.00; GW-DET-004 recalibrated the unclip on validation.)** **Thin-kernel unclip calibration.** With the DBNet shrink ratio r = 0.4 a line's label kernel is thin. The exact inverse of the shrink multiplies any excess thickness of the predicted region by 1/r² = 6.25, while DBNet's unclip ratio 1.5 assumes a region much thicker than the kernel. Which one fits depends on the trained probability map, which is unknown before training, and a wrong unclip mis-sizes boxes and costs F1@0.5. | M | M | Two pre-registered operating points (`dbnet15`, `inverse10`) scored from the same forward pass, with max selection on validation (EXPERIMENT_PROTOCOL §7); a kernel-excess diagnostic on every validation pass; the `BOX SIZE MISMATCH` flag; the label ceiling gated on the selection metric before any GPU run; Phase 9 calibrates `bin_thresh` and `unclip_ratio` on validation from saved candidates and cached probability maps | `BOX SIZE MISMATCH` raised; the label-ceiling gate fails | 8, 9 |
| R-22 | **(Still open after Phase 9: HierText validation has no curved line annotations, so GW-DET-006 could not compare `poly` with `quad`; Phase 14 uses `quad`.)** **Curved GDC lines under a rectangle box output.** GDC, the Phase 14 test set where nothing may be tuned afterwards, has curved, densified line polygons from phone photos. A rectangle around a long curved line can fall below IoU 0.5, so detection would score worse than it reads, with no chance to fix it after the test. | M | M | `det.post.box_type: poly` (the kernel contour offset by the same unclip distance) exists from Phase 8, and every saved candidate keeps its simplified contour, so Phase 9 compares `quad` and `poly` on validation, including its most curved lines, and fixes the Phase 14 setting before GDC is read. All GW-DET runs use `quad`, the rectangle Phase 10 rectifies | Phase 9 finds `poly` ahead of `quad` on curved validation lines | 8, 9, 14 |
